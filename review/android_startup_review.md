# Android 启动与连接体验分析

日期：2026-10-11。目标版本：0.3.18。初步分析基于 0.3.17；用户随后授权实现启动优化，并明确要求手机前台等待时，电脑启动能触发自动连接。

## 当前结论

已配对启动缺少本地连接界面和应用控制的等待上限，足以解释“长时间空白，之后才显示失败引导”的行为。实际等待时长尚未在用户手机测量；WebView 初始化本身是否另有耗时也尚未实测。

初步分析证据（0.3.17 历史基线；行号不代表修改后的当前源码，路径相对项目根目录）：

- `android/app/src/main/java/com/yuzhounh/linkflow/MainActivity.java:179–186`：创建并显示 WebView，读到已保存配对后直接连接；仅未配对时加载本地欢迎页。
- 同文件 `209–212`：`connectToHost()` 仅设置标志并调用 `web.loadUrl(pairingUrl)`，没有连接状态视图、取消或截止时间。
- 同文件 `127–131`：主文档发生网络错误之后，才提示失败并调用 `showWelcome()`。没有实现主文档 HTTP 错误处理。
- 同文件 `351–393`：粘贴配对已有后台 `/api/system/info` 探测，连接/读取超时分别为 8 秒；自动连接和扫码未统一复用它。分别设置超时不能等同于整次操作的总时限。
- 同文件 `431–437`：扫码等调用 `acceptPairing()` 后直接保存并加载；新配对保存时机应随统一连接流程一起明确。
- `android/app/src/main/java/com/yuzhounh/linkflow/Notice.java:14,37–49`：错误信息以约 2.2 秒的顶部通知呈现；截图中覆盖品牌区域，不适合作为持续连接状态。
- `android/app/src/main/assets/welcome.html:5`：失败后回到首次配对引导，扫码、粘贴优先于重连，容易让已配对用户误以为需要再次配对。
- `static/js/app.js:253–285`：网页加载后的 WebSocket 重连已有逻辑，但网页尚未获取时该逻辑无法解决启动白屏。
- `server/App.cs:640–660`：现有信息接口返回服务状态、版本和电脑名称；无需为第一轮优化新增服务端接口。

## 建议的用户流程

1. 无配对：显示现有本地欢迎页，扫码或粘贴连接。
2. 有配对：立即显示本地连接界面，标题“正在连接已配对电脑…”，可取消等待或更换电脑。
3. 探测失败：原地转为“暂时无法连接电脑”，说明“请确认电脑已运行 LinkFlow，并与手机连接同一局域网”。主按钮“重试连接”，次要入口“更换电脑”。保留原配对，不退回首次使用引导，也不反复弹错误通知。
4. 探测成功：在本地提示层下加载远端页面，提示“正在加载界面…”。页面可显示且脚本已初始化后移除提示层；实时连接状态交给网页顶部显示。
5. 服务明确拒绝令牌：提示“配对已失效，请重新扫码”，与网络暂时不可达分开。

无法仅凭超时判断电脑已关闭；IP 改变、网络隔离、VPN 路由等也可能导致同样现象。截图有 VPN 标记，但不足以证明 VPN 是原因。

## 优先级 1：立即可见的本地界面与统一连接控制

- 建议使用轻量原生状态视图覆盖/替代尚未准备好的 WebView；品牌、状态和按钮不依赖网络，也不依赖 WebView 完成加载。
- 首次有意义内容的目标为约 0.5–1 秒，需真实手机冷启动验证，不将其写成已达到的性能结果。
- 后台复用现有带令牌的信息接口探测；建议初始连接/读取分别设置约 2 秒，并额外设置整次探测约 4 秒的截止时间。快速拒绝立即显示结果；这些值是初始设计参数，按设备实测调整。
- 页面加载另设约 6 秒的等待上限，始终保留可操作的本地界面。区分网络不可达与页面加载失败。
- 统一自动启动、重试、扫码、粘贴的连接路径。新配对至少经服务身份与令牌检查成功后才保存，失败时保留原配对和输入。
- 使用连接尝试编号与取消处理：重试、更换电脑、退出后，旧线程结果、旧定时器及旧 WebView 回调不得覆盖新状态；超时停止本次加载并清理资源。
- 检查主文档 HTTP 错误、网络错误与证书错误；不能把 `onPageFinished` 单独当作成功或已绘制的证明。
- 下载补收在确认服务可用后启动，避免启动阶段 `onResume()` 提前发起无效补收请求。

Android 官方说明 `onPageFinished` 不保证下一帧已经反映 DOM；`onPageCommitVisible` 也可能只显示背景，且 CSS/图片尚未就绪。因此需结合页面初始化状态与视觉状态回调确定切换时机，而不能直接在任意一个加载回调中移除提示层。[WebViewClient 文档](https://developer.android.com/reference/android/webkit/WebViewClient)

连接超时和读取超时分别约束不同阶段，读取超时不是整个响应的总截止时间。[URLConnection 文档](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/net/URLConnection.html)

## 优先级 2：有限度的自动恢复

- 第一轮实现可先完成明确状态与手动重试，保证最小改动可验证。
- 后续可在失败界面、应用前台期间按 5、10、20 秒间隔安静重试，最多持续约 1 分钟。电脑随后启动时可自动进入；进入后台、主动取消、切换配对时停止。
- 恢复前台或网络切换后可触发一次探测；去重并限制频率，不持续高速轮询。
- 检查局域网是否可用，不以“互联网验证失败”直接判定不能连接电脑；没有外网的 Wi-Fi 也可以传输。
- 保留已经显示的聊天页面在断连时提供状态提示，不因短暂掉线清空它。完整离线聊天缓存属于另一个任务，本次启动优化不依赖它。

## 有边界的验证

- 未配对冷启动：欢迎页可见，不发起空地址连接。
- 已配对且电脑在线：本地状态立即出现，页面准备好后平滑进入，补收正常。
- 电脑程序关闭、电脑关机/地址不可达：都不长期空白；约 4 秒探测预算后显示可操作失败状态，配对仍保留。
- 令牌失效：显示重新配对提示，与普通网络失败区分。
- 接口成功但页面加载失败：提示层不提前消失，页面等待有上限。
- 快速重复重试、取消、更换电脑及前后台切换：旧请求不能回写状态，不重复补收或弹提示。
- 真实手机记录冷启动首次内容时间、离线反馈时间、在线进入时间；检查 VPN 开启与关闭的差异，仅用于判断是否存在额外网络影响。

## 0.3.18 实现与当前状态

- 已实现原生本地启动/等待/失败界面，4 秒整次服务探测截止、6 秒页面加载截止、配对失效提示、取消及重试。
- 已统一启动、扫码、粘贴与重试的服务验证；失败保留旧配对，新配对经信息接口成功校验后保存。
- 本地界面先绘制一帧，再初始化 WebView。远端网页在不透明的本地提示层下保持渲染；页面就绪同时检查当前导航编号、脚本初始化和视觉状态，并等待下一动画帧再移除提示层，修复连接成功后首帧可能空白的问题。旧电脑端也可通过现有在线/下载状态兼容。补收仅在界面准备好后启动。
- 用户进一步明确的方案已实现为前台局域网上线通知：电脑 HTTP 服务就绪后在实际局域网适配器发送 3 次有限 UDP 广播，手机阻塞等待数据包；没有周期性 HTTP 轮询。
- 手机收到匹配已配对地址/标识的通知后发送一次随机挑战，电脑使用已有配对密钥签名；验证成功后调用连接流程，可立即替换尚未结束的旧连接探测。广播/响应均不发送配对令牌。
- 使用 UDP 5840（电脑）与 5839（手机），只接受原配对 IPv4 地址。此轮不增加云端推送、后台服务、电脑 IP 漂移发现或网络切换基础设施。更改电脑 IP 后重新扫码；防火墙/路由器阻断广播时保留手动重试。
- 手机连接成功、手动取消、进入后台或关闭时释放监听及 Wi-Fi 接收锁。用户取消后不再自动连接，手动重试重新启用。
- 原“优先级 2”里的定时重试属于历史候选，已由用户选定的事件触发方案替代，不实施。
- 最终 Android Release/Debug 构建与 Lint、Windows 构建/发布已通过；Lint 为 0 错误、12 警告，Windows 保留已有 NuGet 审计源不可达及 WindowsBase 引用警告。APK v2 签名验证通过。

### 最终验证与交付

- 真实隔离服务 + Android 15 模拟器验证：手机先等待、电脑服务随后启动、无需任何按钮点击，通过上线通知自动接入；不同模拟器负载下，从通知发送到服务端确认 WebSocket 建立约 3.3–5.1 秒。修正页面切换后截图确认“已连接电脑”与输入栏可见；最终首帧改动后另确认启动立即提供本地“正在连接电脑”界面，未重复运行未受影响的协议检查。
- 模拟器以 UDP 转发代替物理 Wi-Fi 广播传输，验证的是实际通知、随机挑战、签名、HTTP 验证及 WebSocket 接入链路；不能据此宣称所有真实路由器都能送达广播。真实手机、VPN 开关及家庭 Wi-Fi 广播送达待用户安装后实测。
- 无响应探测、整体等待截止、保留配对、手动取消、取消后忽略通知、恢复重试、错误签名忽略、配对令牌失效、主文档 HTTP 失败及界面未就绪超时均已验证。最终非阻塞取消另经 Java 网络回归通过。
- UIAutomator 在访问已加载 WebView 时有测试驱动崩溃/空树，因此连接完成以真实服务端 WebSocket 客户端和已保存配对确认，并检查截图；未把失败的 UIAutomator 输出写为通过。
- 可复用事件测试：先构建 `tests/AndroidStartupFixture/AndroidStartupFixture.csproj` 和 Android Debug；仅使用 `emulator-5554`，安装 `.startupcheck` 调试包、配置 `adb -s emulator-5554 emu redir add udp:15839:5839`，运行 `python tests/android_startup_event_check.py --exact`。省略 `--exact` 可检查错误签名及取消/恢复。测试服务和手机数据与用户实际聊天隔离。
- Java 探测回归：将 `HostProbe.java` 与 `tests/HostProbeRegression.java` 编译至 `android/app/build/probe-regression`，运行 `com.yuzhounh.linkflow.HostProbeRegression`，验证认证、401、禁止跟随重定向、读取超时及取消。
- Windows 交付路径：`dist/LinkFlow-0.3.18-windows/LinkFlow.exe`；此源码工作区构建目录通过 `AppPaths.Find()` 向上使用现有项目 `static/` 与 `data/`，没有单独复制一套用户数据，也没有重启正在运行的用户程序。启动新版前须退出旧电脑程序。

- 当前状态：实现和本地验证完成，未推送/发布，未安装到用户真实手机。电脑端及 APK 都更新至 0.3.18 后，现有有效配对可继续使用。
